# HTTP/WebSocket 隧道传输实施计划

> 状态：实施中。阶段 0/1 已完成；阶段 2 正在加入 WebSocket 消息/连接上限、握手超时与保留域名冲突防护。详见 [代码路径审查](./http-websocket-transport-code-audit.md)。  
> 目标仓库：`jiangood/http-tunnel`

## 1. 背景与目标

当前项目使用独立 TCP 端口（默认 `2333`）承载客户端与服务端之间的隧道协议，HTTP 入口（默认 `80`）根据请求的 `Host` 路由业务流量。

本计划拟增加一种可选的 **HTTP/WebSocket 客户端—服务端传输模式**，让客户端通过指定控制域名主动连接服务端的 HTTP 入口。服务端直接复用自身的 HTTP 监听端口，并依据 `Host` 区分控制流量与普通业务流量，无需为了该功能再增加一个公网端口或强制部署 Nginx。

### 目标

- 保留现有 TCP 传输模式及默认行为，确保兼容现有客户端和部署。
- 新增可选 WebSocket 传输模式，优先使用一个持久的双向连接承载隧道协议数据。
- 控制域名与业务域名共用 HTTP 入口端口，通过 `Host` 和专用路径分流。
- 尽可能复用现有认证、控制命令、转发规则和会话管理。
- 具备超时、心跳、断线重连、资源限制和可观测性。
- 先实现 WebSocket；只有遇到真实的网络兼容性需求后，再评估 HTTP 长轮询降级。

### 非目标

- 不替换或删除现有 TCP 模式。
- 第一阶段不实现长轮询。
- 不承诺 WebSocket 能穿透所有代理或网络策略。
- 不在本次计划中自动申请或管理 TLS 证书。
- 不把 Host 头当作认证手段。
- 第一阶段不改变普通 HTTP 业务域名的现有转发行为。

## 2. 现有能力与需要区分的概念

从当前 README 和代码入口看，项目已经具有：

- `server_port`（默认 `2333`）：客户端连接服务端的原有 TCP 端口。
- `http_port`（默认 `80`）：普通 HTTP 业务入口。
- 根据 HTTP `Host` 路由到隧道或服务端代理的能力。
- 对被转发业务请求中的 WebSocket / HTTP Upgrade 的支持。

**注意：现有“支持转发 WebSocket”不等于“客户端到服务端的隧道控制连接已经使用 WebSocket”。** 本计划新增的是后一种传输方式；两者要分别验证，避免把业务流量 Upgrade 和隧道传输协议混为一谈。

## 3. 目标架构

```text
                         同一 HTTP 监听端口（默认 80）
                                      |
                         +------------+------------+
                         |                         |
              Host: control.example.com   Host: app.example.com
              Path: 专用控制路径            普通 HTTP 业务请求
                         |                         |
                 WebSocket 握手与认证       现有 Host 路由逻辑
                         |                         |
                 隧道协议数据传输          对应客户端 / 本机代理
                         |
               客户端主动建立连接
```

- `control.example.com`：专用控制域名，DNS 指向服务端。
- `app.example.com`：普通业务域名，DNS 同样指向服务端。
- 两个域名共用 `http_port`，服务端在 HTTP 层先匹配 Host，再执行对应处理器。
- 控制连接使用专用路径 `/_http-tunnel/v1/connect`，仅允许 WebSocket 握手进入控制处理器。
- 未配置的控制 Host / 路径应明确拒绝，不应意外落入普通业务转发逻辑。
- 若 80 端口由本进程直接监听，就不需要为此功能配置 Nginx。若部署环境已有 TLS 终止层，未来可通过 HTTPS/WSS 入口接入，但不作为首版前置条件。

## 4. 传输协议设计原则

### 4.1 优先复用现有协议语义

在阅读现有 `protocol`、客户端连接流程和服务端会话管理后，确定哪些消息与 TCP 连接实现耦合。优先复用现有认证、握手、控制命令和数据帧语义；不要未经分析就把原始 TCP 字节流直接当作 WebSocket 消息。

需要明确：
- WebSocket message 与现有协议帧的边界关系。
- 控制消息、数据消息及连接关闭事件的编码方式。
- 单个 WebSocket 连接是否可以承载多个逻辑流；若可行，如何用流 ID 关联。
- 是否需要把现有控制通道和数据通道合并到一个 WebSocket；如果现有设计依赖多个 TCP 连接，应在设计评审中说明兼容方案。
- 消息最大尺寸、每连接缓冲上限、队列满时的背压行为。

### 4.2 连接生命周期

首版至少需要：
- WebSocket 握手与身份认证。
- 定期心跳或等效的活性检测。
- 连接关闭、超时和异常时清理会话及转发资源。
- 客户端指数退避重连，避免服务端故障时大量客户端同时重连。
- 明确重连后是恢复会话，还是重新注册并重建逻辑流；首版可以选择更简单且可靠的重新注册。
- 防止同一客户端重复连接时产生未定义的会话状态。

### 4.3 Host 路由与认证

- 先严格校验 Host 和控制路径，再执行 WebSocket Upgrade。
- 控制域名只是路由选择，不构成授权；仍必须验证现有 token 或经过设计确认的等效凭证。
- 不在日志中输出 token 或其他敏感凭证。
- 对未认证连接、重复注册、异常帧和资源耗尽提供明确的失败处理。
- 考虑请求头伪造、Host 混淆、路径混淆和重放等风险。

## 5. 配置草案（命名待代码审查后确定）

下面只是讨论用的配置形态，不是最终配置规范：

```toml
# 原有 TCP 模式保持兼容
server_port = 2333

# 现有 HTTP 业务入口；控制 Host 也复用这个监听端口
http_port = 80

# 新增字段示意，具体名称及默认值待定
# websocket_enabled = true
# control_host = "control.example.com"
# control_path = "/_http-tunnel/v1/connect"
```

客户端也需要一个明确的传输选择和控制端点配置，例如传输模式、服务端 Host/域名、路径与端口。字段设计需兼顾旧配置文件：升级后不应因为缺少新增字段而改变现有 TCP 行为。

需要特别说明：首版若使用 `ws://` 经由 80 端口，传输内容是明文，Token 和隧道数据可能被网络中间方读取或篡改。应在文档中明确风险，并评估端到端加密或后续 WSS 支持；“不要求用户申请证书”是易用性目标，不代表明文公网传输天然安全。

## 7. 测试清单

- 原 TCP 客户端连接和已有配置继续工作。
- HTTP 业务域名的普通 GET/POST 请求继续正确路由。
- 业务域名的 WebSocket Upgrade 继续正常转发。
- 控制 Host + 正确路径可建立 WebSocket；错误 Host / 路径返回明确错误。
- 错误 token 无法注册或交换隧道数据。
- 客户端异常退出后服务端及时清理状态。
- 服务端重启后客户端能够按退避策略重连。
- 大消息、慢消费者和大量并发连接不会导致无界内存增长。
- 控制域名请求不会被当作普通业务请求转发。
- 旧版本配置在不新增字段的情况下保持旧 TCP 行为。

## 8. 风险与待决事项

1. **安全：** 80 端口上的 WS 是明文。需要在易用性与公网传输安全之间做明确选择，不能把 Token 认证误认为加密。
2. **网络兼容性：** 一些代理会禁止 WebSocket Upgrade 或主动终止长连接。先实现 WebSocket，基于实际失败情况再评估长轮询。
3. **协议耦合：** 现有 TCP 实现可能依赖控制与数据连接的分离。是否合并连接必须由代码审查和原型验证决定。
4. **Host 与域名配置：** 控制域名和业务域名需要解析到同一服务端；服务端应严格处理 Host。
5. **端口冲突：** 若已有进程占用 80，服务端无法同时绑定同一地址和端口；需要部署时处理监听地址或端口规划。
6. **范围控制：** 首版以复用现有隧道协议并完成 HTTP 业务穿透为目标，不顺带重构原 TCP 传输层。
